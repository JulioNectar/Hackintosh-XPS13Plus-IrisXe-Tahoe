# Changelog

Every change is tested on the real XPS 13 Plus 9320 before it is marked **confirmed**. Status values:
**confirmed** (works on hardware), **testing** (built and installed, being evaluated), **reverted**, **superseded** (replaced by a later entry).
The full story behind each item is in [docs/HISTORY.md](docs/HISTORY.md).

| 2026-10-26 | **Sustained power limit option** (XE-PM `ngreenpm=W` / `ngreenpmpl1=W`; the repo `config.plist` now uses `ngreenpm=22`): without Dell's Windows thermal software (DTT) the BIOS leaves the MCHBAR PL1 at 17.5 W (MSR 0x610 PL1 is 64 W; the lower applies). XE-PM writes the MCHBAR PL1 (0x59A0, only if unlocked) 20 s after boot. 45 s all-core load: 17.5 W 7079 at 75 °C, **22 W 8423–8706 (+19–23 %) at ~85 °C**, 25 W 8078 at 93 °C, 28 W 7549 at 94 °C (thermal limit). The GPU was checked too: at 1300 MHz it already draws ~19 W and the package reaches 93 °C in seconds, so the "ICCMAX/PL4" GPU limit was left alone. `sysctl debug.xepm.pl1_set` shows the written value | confirmed |
| 2026-10-26 | **CPU turbo and idle power profile** (NootedGreen **XE-PM**, `-ngreenpm`, on in the repo `config.plist`): XCPM, written before hybrid CPUs, writes `IA32_HWP_REQUEST` max/desired in 100 MHz units, but hybrid P-cores count HWP performance in ~78.7 MHz units (HWP highest 64 = 5.0 GHz), so the turbo limit 50 meant ~3.9 GHz; its EPP 0x80 also clips one-core turbo on ADL/RPL mobile (Intel, Linux 5.17 intel_pstate), and energy-efficient turbo held the top bins. XE-PM routes the XCPM routine that writes the request (`_xcpm_enable_pstate_ctrs+0x1190`, checked byte for byte) and rescales max/desired on P-cores, writes EPP 0 (`ngreenpmepp=N`, `sysctl debug.xepm.epp`) and sets `MSR_POWER_CTL` bit 19. It also enables C8/C10 and disables the non-existent C3 in XCPM's idle table (`_xcpm_cstate_table`), and puts driverless IPU/GNA/ISH/DPTF/Thunderbolt-DMA functions in D3hot. Applied 20 s after boot (with the HWP part on from the start, an early XCPM call before HWP enable made the machine reset). Geekbench 7 single-core 1269 → 1697 (+34 %), multi-core 5859 → 6148; one-thread clock 3.3 → 4.3–4.85 GHz; idle package ~4.6 → ~3.3 W. Raising PL1 to 28 W did not help (94 °C, thermal limit) | confirmed |
| 2026-10-26 | **Audio DSP idle power-down** (AudShim 0.9.2): the DSP, SoundWire links and amps stayed powered with DSP clock/power gating disabled for as long as coreaudiod ran. Now gating is re-enabled after firmware boot (as Linux `hda_dsp_post_fw_run`) and everything is torn down after 30 s without a stream (`audshimidleoffms=N`, 0 = never); the next sound brings it back up in ~1–2 s. HDA power-gating domains now gate at idle. Off: `-audshimnopg`, `audshimidleoffms=0` | confirmed |
| 2026-10-25 | **OLED brightness over AUX, experimental** (NootedGreen **XE-AUXBL**, [#15](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/issues/15)): OLED panels ignore the PWM backlight pin, so the brightness keys did nothing. With `ngreenauxbl=3` the level macOS writes to the PWM duty register is also sent to the panel over the eDP AUX channel through the Intel HDR TCON interface, as Linux i915 does (DPCD 0x344 bit 4, nits at 0x354; maximum `ngreenauxnits=N`, default 400). `ngreenauxbl=1` uses the VESA interface instead (0x720–0x723). It arms only when the panel advertises the interface, and the AUX writes run on a thread call with Apple's own `readAUX`/`writeAUX`. On the XPS LCD panel (PWM only) both modes stay unarmed or have no effect, so the effect itself is not tested here. ioreg `xe-dpcd700-*`, `xe-dpcd340`, `xe-auxbl-*`. Off by default | testing |
| 2026-10-25 | **Short dash artifacts when zooming images fixed** (NootedGreen **XE-ROWCHK**, [#9](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/issues/9), reported by iqsanfm): SIMD32 compute kernels that use a private array read one stale register (lanes 8–15, `.x` channel), so their results changed from run to run. Core Image's Lanczos downscale is such a kernel: short faint dashes in Preview/Photos, worst when zoomed out. Cause: the Gen12 workarounds Wa_1606931601 / Wa_1508744258 (`GEN8_ROW_CHICKEN2` 0xe4f4 bits 14\|15, disable early read / read suppression) were never set: upstream has them in dead code and Apple's driver doesn't set them. Now written after every render-engine start, with the render power well held awake by NootedGreen's own forcewake bit (a write without forcewake is lost). Test: a private-array kernel went from 6/6 runs differing (~60 000 px) to 0/6, and Core Image Lanczos GPU vs CPU from ~300 bad pixels per render to 0; artifacts gone in Preview. ioreg `xe-rowchk-post` shows 0xc000 in the low bits. Off: `-ngreennorowchk` | confirmed |
| 2026-10-25 | **Dock badge numbers and other trilinear-scaled images were invisible** (libxedrv v19, [#10](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/issues/10), reported by iqsanfm): for layers with `minificationFilter = trilinear` Core Animation creates a zero-copy texture on the image's memory with a full mip chain (`newTiledTextureWithBytesNoCopy`, 108×108 → 7 levels); the 16.0.32 driver never fills levels 1+, so the trilinear sample read empty levels. libxedrv now makes its own copy with level 0 uploaded and the other levels generated (`generateMipmapsForTexture:`).
